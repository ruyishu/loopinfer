# LoopInfer 小评测报告（H1 / 2026-11-18，v0.3）

- 模型：`models/Ouro-1.4B`（4 loops，bf16）
- 硬件：单卡 NVIDIA H20 96G
- 代码：v0.3.0（prefill/decode 拆分、按需分页 + 抢占、按需构建页表、chat/logprobs/stop、分阶段计时）

## TL;DR

| 结论 | 数据 |
|---|---|
| 与官方实现数值一致 | fp32 32/32 argmax 相同，最大 logprob 误差 2.29e-05 |
| GSM8K 没有退化 | 100 题 20/100，和 v0.2 相同；与 HF 逐题判定一致 **99/100**（v0.2 是 93/100） |
| 服务端吞吐 | 49.1 / 114.7 / 208.7 tok/s（并发 1/4/8） |
| 服务端相对进程内 | 0% / −6% / −8%，说明「服务端 115 对进程内 185」来自两次测量请求量不同，不是 HTTP 开销 |
| 每步耗时构成（并发 4） | 31.7 ms = GPU 等待 18.9 + 内核发射 4.8 + 页表准备 0.5 + 提交 0.04 + 其余 |
| 长上下文代价 | 2048 入时每步 47.7 ms，发射时间涨到 23.9 ms（逐层 gather + masked_fill） |
| Triton 分页注意力 | 数值正确（fp32 1e-4），但比 SDPA 慢约 3 倍，默认关闭 |

## 1. 数值对齐（vs 官方 Transformers）

| dtype | 对比位置 | argmax 一致 | 最大 logprob 误差 | 最大隐状态误差 |
|---|---|---|---|---|
| float32 | 32 | 32/32 | 2.29e-05 | 1.14e-05 |
| bfloat16 | 64 | 61/64 | 8.81e-01 | 4.30e-01 |

CUDA Graph 打开与关闭，8 条 prompt 贪心解码逐 token 完全相同。

## 2. GSM8K 准确率（100 题，贪心，192 新 token）

| 引擎 | 答对 | 与 HF 逐题判定一致 | 与 HF 答案完全相同 |
|---|---|---|---|
| HF Transformers | 21 | — | — |
| LoopInfer v0.2 | 20 | 93/100 | 75/100 |
| LoopInfer v0.3 | 20 | **99/100** | 85/100 |

v0.3 与 v0.2 的生成文本只有 56/100 完全相同：prefill 与 decode 拆成两个子批后，GEMM 的 batch 形状变了，bf16 下末位舍入随之变化。这是 r1 级差异（每行运算不变、批组成变化），不影响与参考实现的一致性——上表说明 v0.3 反而更贴近 HF。

## 3. 服务端性能（Ouro-1.4B，32 入 / 32 出，贪心）

| 并发 | v0.2 服务端 | v0.3 服务端 | v0.3 进程内 | 服务端 / 进程内 |
|---|---|---|---|---|
| 1 | 48.4 | **49.1** | 49.5 | 99% |
| 4 | 115.4 | **114.7** | 122.5 | 94% |
| 8 | 213.1 | **208.7** | 226.8 | 92% |

进程内用与 `perf.py` 相同的请求组合（每客户端 2 个请求、1 次预热），只用 `Engine.submit().wait()`，不经过 HTTP。

## 4. 每步耗时构成（`/metrics` 的 `step_ms_*`，并发 4）

| 阶段 | 毫秒 | 说明 |
|---|---|---|
| prepare | 0.54 | 上传页表、在设备上构造槽位与因果掩码 |
| forward | 4.77 | 一次 CUDA Graph 发射（内核在 GPU 上异步执行） |
| sample | 18.89 | 取回 logits 的同步点，实际是等 GPU 算完 |
| commit | 0.04 | 记账、推流事件 |
| step | 31.65 | 整步；差额来自 prefill 步骤的缓冲区分配等 |

结论：GPU 计算是主项，CPU 侧每步只剩约 5 ms。要继续提单流速度，只能减少 GPU 上的 kernel 与访存（精确融合、更好的注意力），单纯优化 Python 调度已无空间。

## 5. 长上下文（2048 入 / 32 出，并发 1）

| 指标 | 32 入 | 2048 入 |
|---|---|---|
| 每步耗时 | 18.2 ms | 47.7 ms |
| 其中发射 | 2.5 ms | 23.9 ms |
| 其中 GPU 等待 | 15.3 ms | 23.0 ms |
| 输出吞吐 | 54.9 tok/s | 14.3 tok/s（含 2K prefill） |

发射时间随上下文线性上涨，来自每层每轮对全部历史 KV 的 gather 与 masked_fill。这是下一个该动的地方。

## 6. Triton 分页注意力（`--attention triton`，默认关闭）

- 数值：随机数据、GQA、fp32 下与 SDPA 相差 1e-4；bf16 下与 SDPA 生成的 token 8 条 prompt 中 7 条不同——属于不同 kernel 的舍入差异，不是实现错误。
- 速度：每步 59.6 ms，比 SDPA 路径慢约 3 倍。原因是没有用张量核、每行每头各自读一遍 K/V。
- 结论：保留为实验开关，默认走 SDPA。要真正赢，需要写成 FlashDecoding 风格的 kernel（更大的 BLOCK_N、bf16 张量核、按 kv 头共享）。

## 7. v0.3 做了什么

- **prefill/decode 拆分子批**：混入 prefill 不再把整批拖回 eager 路径。
- **按需分页 + 抢占**：按实际增长分配页；池子不够时抢占最新请求并从 prompt 重跑，抢占期间关闭准入避免抖动；流式请求不能回滚，改为直接失败。
- **页表在设备上构造**：只上传每行标量 + 补齐后的页表，槽位与因果掩码在 GPU 上生成。
- **服务接口**：`/v1/chat/completions`（读 checkpoint 的 chat_template，或 `--chat-template`/`--default-chat-template`）、`logprobs`/`top_logprobs`、`stop`、`n`。
- **可观测**：`/metrics` 增加分阶段耗时、抢占次数、图捕获/回放/淘汰计数。
- **图预算**：`--graph-budget` 限制缓存的图数量，FIFO 淘汰。
- **评测**：新增 `eval/inprocess.py`（与 perf.py 同构的进程内对照）、`eval/compare.py`（跨轮次逐题对照）、`tools/check_attention.py`。

## 8. 还没做

- P2：混合深度 pass（轮间组批、动态深度、自推测）——方案已定，未实现。
- prefix cache（共享前缀复用页表）。
- 长上下文的真正提速：FlashDecoding 风格分页注意力、精确融合算子（RMSNorm/RoPE/SiLU）、prefill 上图。
- 早退与 P3 有损档（默认关闭的实验开关）。
